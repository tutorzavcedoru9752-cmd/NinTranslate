# NinTranslate 1.6.3 闲置后截图响应修复验收

日期：2026-10-15。针对用户安装 1.6.2 后反馈的“闲置一段时间再次截图仍需等待 1–2 秒”。已只读确认当前安装版本为 1.6.2，原生采集进程在运行。

## 原因与测量修正

1. 1.6.2 仍需把整屏像素从采集进程传到 Electron 主进程，再交给隐藏的 Chromium 页面，等待图片加载、恢复显示与窗口绘制。窗口预热没有消除这条跨进程传输和绘制路径。
2. 上一轮 20 次连续测试只间隔 200 毫秒，计时止于窗口显示调用完成，没有覆盖闲置后完整呈现。255 毫秒不能直接代表用户看到画面的等待。
3. 旧采集适配器发生一次超时/退出后会永久禁用原生采集，直到重启应用。已改成冷却后可重试。新的原生选区组件还会自动重启和预热，避免一次异常后一直走慢速备用接口。

复现：1.6.2 闲置 15 秒时，内部显示调用约 373 ms，窗口实际读回完成约 999 ms；闲置 120 秒时，前者约 460 ms，后者约 1176 ms。读回包含额外复制成本，属于上界，不是高速摄影测量。报告保留原始数值和测量边界，不再用内部就绪时间代替用户可见响应。

## 实现

- Windows 新增 `screen-overlay.exe`，使用 Windows 自带 .NET Framework/WinForms 与 Win32 GDI。新框架仅用于截图选区这一性能关键组件，主界面、设置、结果与历史继续沿用现有 Electron/React。
- 屏幕采集、冻结画面、遮罩、选区边框和鼠标交互都在同一原生进程里完成；整屏画面不再经过管道、base64、内存图片协议或隐藏浏览器窗口。
- 每个屏幕预创建隐藏窗口。预热用本地生成的空白位图初始化绘图和字体，不读取桌面、不显示窗口。闲置时不连续截图，也不持续绘制或阻止系统休眠。
- 每次唤起明确恢复原生置顶顺序，避免闲置期间其他应用的置顶窗口改变顺序。
- 选区完成后才裁剪小图，沿用放大、灰度和对比度增强，再以 PNG 交给原来的本地 OCR。C# 使用 GDI+ 高质量缩放，与浏览器 Canvas 的插值实现并非逐像素完全相同，已用实际截图验证识别内容。
- 保留拖动框选、Esc/右键取消、不同 DPI 显示器和全局坐标。截图窗口沿用现有语义配色、字体和圆角提示。
- 主进程校验会话 ID、图片类型与坐标。旧会话和迟到的处理结果不能覆盖新截图。原生和备用选区不能重叠运行。
- 原生进程退出后自动恢复；不可用时退回旧截图层。修复备用采集适配器永久降级的问题。
- 新增最近 50 条纯数值诊断记录，只含版本、时间、后端类型和阶段耗时，不含截图、识别文字、API 密钥；异步写入，不阻塞快捷键；界面不显示耗时。

测试使用合成文字窗口和隔离数据目录，没有停止或替换用户正在运行的 1.6.2，也没有修改其凭据、设置或翻译历史。

## 性能验收方法

第一组旧版复现报告：`capture-idle-v1.6.2.json`。新组件第一次迭代的 15/30/60/120 秒间隔绘制确认分别约 303/300/257/251 ms；之后又优化了空白位图预热和 GDI 绘图，并重新进行屏幕像素对照。

最终对照使用相同的 Win32 读屏探针，在每个屏幕的固定色块确认真正出现了遮罩后才结束计时；包含探针自身的读回开销。两个路径共用同样的生成文字窗口、显示器和探针，不写入桌面图片。旧路径检查立即和 30 秒间隔，新路径检查立即、15/30/60/120 秒间隔。原始结果见交付目录 `capture-visible-comparison.json`。

| 间隔 | 旧 Electron 选区，同一像素探针 | 新原生选区，同一像素探针 | 新原生窗口绘制/合成确认 |
|---|---:|---:|---:|
| 立即 | 708 ms | 368 ms | 190 ms |
| 15 秒 | — | 443 ms | 247 ms |
| 30 秒 | 931 ms | 405 ms | 254 ms |
| 60 秒 | — | 467 ms | 262 ms |
| 120 秒 | — | 506 ms | 307 ms |

每种间隔是一次样本，不是 P95 或硬件性能保证。新原生路径每次首次探针读回就确认了真实选区像素，旧路径两次均需第二次读回才确认。当前 Windows 10 x64 双屏缩放约为 192.5% 和 137.5%；没有降低截图分辨率。

`totalMs` 是逻辑响应：旧路径为显示调用完成，新路径为原生窗口 Show/Update 后经过 DwmFlush 确认。两者终点不同，不能直接计算提速倍数。跨路径比较应使用同一探针的 `composedVisibleMs`；它是带读回开销的可见响应上界，也不等于键盘硬件到显示器发光的延迟。

计时 API 参考：[Microsoft DwmFlush](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/nf-dwmapi-dwmflush)、[Electron 窗口显示和可见性](https://www.electronjs.org/docs/latest/api/browser-window)。
